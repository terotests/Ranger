# The eight measurements

```
npm install --no-save survey-core
npm run rangerforms:timings
node gallery/rangerforms/bench/timings.mjs --branches 2000 --repeat 9
```

```
    what                  size                       ours   surveyjs   note
  ─────────────────────────────────────────────────────────────────────────────────────
  Q1  parse                 2500 questions          28.8 ms          —   text → questionnaire with compiled rules
  Q2  initial evaluation    2000 rules              4.50 ms          —   every rule, once
  Q8  cold start            2500 questions          27.4 ms    1210 ms   text in, ready to answer
  Q3  one answer, settled   in 2500 questions       0.45 ms    51.2 ms   4 rule evaluations
  Q4  cascade               depth 1000              1.94 ms     101 ms   last = 1005
  Q5  validation, read      500 answers             0.27 ms    66.6 ms   ours reads flags settle keeps current

```

Median of five runs after a warm-up. The corpus is generated by the harness,
so the sizes in the table are the sizes that were run.

## Read this before the numbers

**We are not doing the same amount of work, and the difference is the point.**
SurveyJS builds question objects with titles, localization, display values,
CSS classes and an event system, because it is a form *library* and something
has to render. RangerForms builds a dependency graph and an answer state,
because it is an engine and the renderer is somebody else's. A 44× cold start
is mostly that, not cleverness — and it is the argument for separating the
two, which is what the numbers are here to support.

**Q1 and Q2 have no SurveyJS column.** It evaluates the whole form in its
constructor, so parse and first evaluation are one act there and two here.
Reporting our split against their combined figure would flatter us. Q8 — text
in, ready to answer — is the number both are measured on.

**Q5 is reported twice.** Ours settles as answers arrive, so asking "what is
invalid" reads flags that are already current; SurveyJS evaluates on demand.
Comparing a cache against a computation proves nothing, so Q5b re-runs *every*
rule on our side. That is the honest upper bound, and it is the row to read.

**Q6 is the one we lose.** `submissionJson` builds its string a character at a
time; `JSON.stringify` is written in C++. 1.4 ms against 0.75 ms on five
hundred answers, and it would be dishonest to leave the row out because it
does not flatter.

## Q3 is the measurement that matters

Changing one answer in a 2 500-question form:

```
  0.45 ms   ·   4 rule evaluations
```

The four are the rules of that one branch — its follow-up's visibility, its
follow-up's requirement, its calculation, and the check that reads the
calculation. Nothing else in the form is touched, because the dependency graph
knows what depends on what and `settle` walks only that.

The rule count is the number to hold on to. Milliseconds are a fact about this
machine and this JIT; **4** is a fact about the engine, it is asserted by
`EngineTest`, and it is the same on every target the conformance run covers.

An engine without a dependency graph re-evaluates the form. At this size that
is 2 000 rules instead of 4, and the ratio grows with the form — which is why
a naive engine feels fine on a demo and stalls on a real questionnaire.

## What is not measured here

Anything about rendering, because the engine does not render. Anything about
network, storage or a survey server. And the other five targets: these numbers
are the ES6 build under Node, and `CONFORMANCE.md` is the run that shows the
answers are identical on python, go and cpp — how fast they are there is a
separate table nobody has written yet.
