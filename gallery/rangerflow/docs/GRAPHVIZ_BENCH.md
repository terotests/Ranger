## What asking costs

| reference | 500 diagrams | per diagram |
| --- | --- | --- |
| graphviz `dot -Tcanon` (native, parse only) | 115 ms | **0.230 ms** |
| graphviz `dot -Tsvg` (native, parse + layout + render) | 133 ms | **0.267 ms** |
| graphviz wasm `canon` (in process, parse only) | 122 ms | **0.245 ms** |
| graphviz wasm `json0` (in process, parse → structure) | 170 ms | **0.339 ms** |
| graphviz wasm `svg` (in process, parse + layout + render) | 170 ms | **0.340 ms** |
| dotparser (pure JS, MIT) → AST | 47 ms | **0.094 ms** |
| @ts-graphviz/ast (pure JS, MIT) → AST | 60 ms | **0.119 ms** |

@ts-graphviz/ast (pure JS, MIT) → AST throws on 2 of the 15 fixtures in the stream, so 67 of its
500 answers are a thrown error rather than an AST. That is cheaper than parsing, and its
row is therefore a flattering number, not a comparable one.

`dot -V` alone — one process, no diagram — is **8.19 ms**, and the two native rows
above are one process for the whole corpus. Started once per diagram instead, the
CLI would pay that 500 times over: **8.19 ms/diagram** of fixed cost before any DOT is read.

The WebAssembly module loads once, in **80 ms**, and then answers in process —
no fork, no exec, no JVM, and the same answers as the native program (the table above).
