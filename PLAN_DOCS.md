# PLAN_DOCS — generated language documentation site

Status: implemented. The pipeline, the site and the deployment are in the tree
(`docs/`, `.github/workflows/deploy-pages.yml`). This document is the design
record; `docs/README.md` describes the code as it is. Section 11 states which
milestones are done.

Scope: a documentation site that is generated from the operator sources of the language —
`compiler/Lang.rgr` and the library files that declare operators — published to GitHub
Pages on every Ranger release, next to the playground but on a different URL.

The site has two kinds of content:

1. **Generated reference.** One page per operator group, built from the operator
   definitions in `compiler/Lang.rgr` and in the `lib/` sources, with real compiler
   output for each target language. Nothing in this part is written by hand except the
   prose.
2. **Handwritten guides.** Language description, use cases, toolchain. Written in
   ASD-STE100 Simplified Technical English.

The generated part is the reason this document exists: the operator set is large,
it changes with the compiler, and hand-maintained tables go stale. The examples must
come out of the compiler that is in the tree, not out of a text file that somebody
updated once.

Four limits of `operators.md` make it insufficient as the reference:

- **One source only.** The file documents the operators that the compilation of that one
  program registered. Half of the operator set of the language is in the libraries and is
  absent: 343 of 680 definitions.
- **No output examples.** The reader sees `%  | int | (left:int right:int)`, but not
  the Go, the Rust or the Python code that the operator produces.
- **Almost no prose.** Only 12 of 337 core definitions have an `@doc('…')` annotation.
- **No target coverage data.** A template can exist for Go and not for Kotlin. The
  table does not show this, so the reader finds the gap at compile time.

### 1.1 Operator sources

An operator does not have to be in `Lang.rgr`, and the language has **two** operator
mechanisms:

| Mechanism | Declaration | Portability |
| --- | --- | --- |
| **A. Template operator** | `operators { }` / `commands { }`, one emission string per target | Manual. A target with no template and no `*` fallback writes no code |
| **B. Type method** | `operator type:<T> <scope> { fn … }`, an ordinary Ranger body | Every target that compiles the library |

Mechanism B is the one that `operators.md` and the first version of this plan both
missed. The counts below are mechanism A; the type methods are counted after the table.
Both are measured with the Ranger parser over the current tree:

| Source | Definitions | Different names | Availability |

| `compiler/Lang.rgr` | 337 | 207 | Always. The core of the language |

| `lib/stdlib.rgr` | 7 | 3 | `Import "stdlib.rgr"`. Union type `case` and `cast` |
| `lib/Engine3D.rgr` | 129 | 112 | `Import "Engine3D.rgr"` |

Mechanism B adds **158 type methods** in 12 files, among them the collection operations
that a reader looks for first: `map`, `filter`, `reduce`, `any`, `all`, `slice`,
`groupBy`, and the map helpers `values`, `map_length`, `get_or`. Six of the files that
declare them hold no `operators { }` block at all (`ImmutableVector`, `Time`,
`TypedArrays`, `IndexedDB`, `SQL`, `ACEEditor`), so a registry that looks for that block
only does not see them. `docs/sources.json` names 22 sources, and the registry check
looks for both block forms.

The list is data, not code: `docs/sources.json` names each source, its import
statement, its documentation group and whether it is available in every program. A new
library is one more entry in that file, and the reference then covers it.

## 2. Framework decision: Astro Starlight

**Decision: Astro Starlight.** The alternative in the request was Docusaurus. Both are
free and both do the job, so the decision comes from four properties of this repository.

| Property | Starlight | Docusaurus | Weight for Ranger |
| --- | --- | --- | --- |
| Build system | Astro, Vite based | Webpack + React | The playground is already Vite + TypeScript. One build system, one mental model, one set of lockfile problems. |
| Generated code blocks | Expressive Code `<Code code={…} lang={…} title={…} />` takes the code as a **prop**, so a string from JSON becomes a code block with no file on disk | `<CodeBlock>` accepts children; generated content usually goes through MDX files | The reference is generated data. A component that takes data is a better fit than a component that takes a file. |
| Target tabs | `<Tabs syncKey="target">` keeps the selected tab across every page of the site | `<Tabs groupId>` does the same | Equal. Both let the reader choose "Go" once and read the whole reference in Go. |
| Search | Pagefind, built in, static, no external service, no index size limit for a site of this size | Local search needs a plugin, or Algolia DocSearch (an external account) | GitHub Pages is a static host with no server. Pagefind needs no account. |
| Versioned documentation | Not built in. The `starlight-versions` plugin exists but is in early development | Built in and mature (`docusaurus docs:version`) | The one point for Docusaurus. Section 9 handles it without a plugin. |
| Dependency weight | Astro + Starlight, no React needed | React 18 + MDX + Webpack toolchain | Smaller install, faster CI. |

VitePress was the third option. It is lighter still, but the code block API is weaker
for generated content and the sidebar/i18n structure is less complete. Starlight wins on
the Expressive Code component alone.

**The versioning gap is accepted**, and Section 9 gives the replacement: the site
documents the current release, shows the version in the header, and carries a generated
"changes between releases" page produced by a diff of two operator models. If versioned
documentation becomes necessary later, `starlight-versions` can be added without a
change to the generator, because the generator writes plain MDX into the content
directory.

References: [Starlight plugins](https://starlight.astro.build/resources/plugins/),
[Expressive Code component](https://expressive-code.com/key-features/code-component/),
[starlight-versions](https://github.com/HiDeoo/starlight-versions).

```js
// docs/site/astro.config.mjs
export default defineConfig({
  site: "https://terotests.github.io",
```

`base` must end with a slash, and every internal link must include it. Starlight adds
the prefix to its own navigation. Handwritten links use the Starlight link helpers or
absolute paths that start with `/Ranger/docs/`.

## 4. Generator architecture

Four stages. Each stage writes a file, so each stage can be run, tested and debugged
alone. Stage B is the only slow one.

```
docs/sources.json ──► A1. parse   ─┐
  compiler/Lang.rgr                ├─► A3. join ──► operators.json ──┐
  lib/*.rgr        ──► A2. compile ┘                                 ├─► C. render ──► reference/**.mdx
                                                                     │                 src/data/*.json
docs/examples/**.rgr ──────────────► B. compile ──► examples.json ───┤
docs/descriptions/**.md ────────────────────────────────────────────┘
                                              └─► D. report ──► coverage.json + exit code
```

### Stage A — operator model extraction

`docs/tools/extract-operators.mjs`

The stage has two readers and one join. The two readers see different things, and the
reference needs both.

#### A1 — the Ranger parser reads each source file

The compiler exports its own parser, and the parser can read an operator source with no
compilation and no program:

```js
const { SourceCode, RangerLispParser } = require("./dist/api.js");
const sc = new SourceCode(fs.readFileSync("compiler/Lang.rgr", "utf8"));
sc.filename = "compiler/Lang.rgr";
const p = new RangerLispParser(sc);
p.parse();                       // 111 ms for 5852 lines, had_error = false
```

Measured against the current tree: `Lang.rgr` gives 337 definitions in
`language → commands`, and `lib/Timers.rgr` parses in 3 ms and gives 6 definitions in its
`operators` block. The node shape of one definition is:

| Child | Content | Example for `%` |
| --- | --- | --- |
| 0 | operator name | `%` |
| 1 | implementation name, `_` if none | `_` |
| 2 | return type | `int` |
| 3 | argument list node | `left:int right:int` |
| 4 | `templates` block | `es6`, `go`, `rust`, … |

The parser is the primary reader for four reasons:

1. It works on **any** file that has an `operators { }` block. It does not need the file
   to be importable, compilable or reachable from a probe program.
2. It gives the **template source text verbatim**, which is what the "target support"
   section and the contributor documentation need.
3. It gives **source order, line numbers and comments**. The section comments in
   `Lang.rgr` (`; Bitwise operators for integer manipulation`, and the 40-line header
   that describes the template commands) are documentation that is written already, and
   a compiled context throws them away.
4. It is fast: the full set of 16 sources parses in well under one second, so the model
   can be rebuilt on every file change during `docs:dev`.

#### A2 — the compiler adds the semantic layer

The parser sees text. It does not resolve overloads, it does not know which category
`ng_RangerDocGenerator` puts an operator in, and it does not know whether the operator is
registered at all. For that, one probe program per source is compiled in process, and the
operator set is read from the writer context:

```js
const ops = await res.ctx.getAllOperators();   // → 415 descriptors for Lang.rgr + stdops.rgr
```

The probe program for a library imports that library:

```ranger
Import "JSON.rgr"
class Probe { sfn m@(main):void () { } }
```

The operators that the probe registers, minus the operators that the core probe
registers, are the operators that the library adds. Each descriptor carries
`node.getFilename()`, so the origin is also available directly and the difference is a
cross-check, not the only method.

#### A3 — the join

The two readers are joined on `(file, line)`. The parser record is the base, the compiled
descriptor adds `category`, the resolved type strings and the registration state. A parsed
definition with no compiled descriptor is reported: it means the operator exists in the
file but no program can reach it. A compiled descriptor with no parsed definition is also
reported: it means a source is missing from `docs/sources.json`. Both conditions are
counted in Stage D, so a new library cannot enter the tree unnoticed.

For each operator the model holds:

| Field | Reader | Example |
| --- | --- | --- |
| `name` | A1, child 0 | `"%"` |
| `returns` | A1 child 2, printed by A2 with the same type printer as `ng_RangerDocGenerator` | `"int"` |
| `args[]` | A1 child 3 → `{ name, type, optional, array_type, key_type, expression }` | `[{name:"left",type:"int"}, …]` |
| `doc` | A1, the `@doc('…')` annotation | `"run this code only in JavaScript"` |
| `targets{}` | A1 child 4, one entry per target, with the template source text | `{ go: "…", rust: "…" }` |
| `comment` | A1, the comment lines above the definition | `"Bitwise operators for integer manipulation"` |
| `source` | A1, file and line | `compiler/Lang.rgr:1342` |
| `library` | A1, the entry in `docs/sources.json` | `{ id: "json", import: "JSON.rgr", always: false }` |
| `registered` | A2, the operator appears in `ctx.getAllOperators()` | `true` |
| `category` | A2, the predicate set of `ng_RangerDocGenerator.createOperatorDoc` | `"numeric"` |
| `id` | computed, see below | `"mod.int.int"` |

**Operator identifiers.** Operator names contain characters that are not valid in a URL
or a file name, overloads share a name, and two libraries can declare the same name (both
`Lang.rgr` and `lib/JSON.rgr` declare `print`). The identifier is therefore
`source id + "/" + slug(name) + "." + arg type list`, for example `core/mod.int.int` and
`json/print.JSONDataObject`. The source id comes from `docs/sources.json`; the core
sources use `core`. The slug table:

| Symbol | Slug | Symbol | Slug | Symbol | Slug |
| --- | --- | --- | --- | --- | --- |
| `+` | `add` | `-` | `sub` | `*` | `mul` |
| `/` | `div` | `%` | `mod` | `=` | `assign` |
| `==` | `eq` | `!=` | `ne` | `<` | `lt` |
| `>` | `gt` | `<=` | `le` | `>=` | `ge` |
| `&&` | `and` | `\|\|` | `or` | `!` | `not` |
| `[]` | `index` | `??` | `coalesce` | `!!` | `force` |
| `null?` | `is-null` | `!null?` | `not-null` | `if!` | `if-not` |

Any other non-alphanumeric character becomes `-`. The table lives in
`docs/tools/lib/opid.mjs` and is covered by a unit test, because the identifier is part
of the public URL and must not change between releases without cause.

The categories keep the section names of `operators.md`, so a reader of the old file
finds the same groups: statements, language switches, operators without arguments,
generic, numeric, bitwise, miscellaneous, string, array, map, boolean. A library
operator gets its library as the first grouping level and the category as the second.

**Macros.** `lib/stdops.rgr` also holds 15 `defn` macros. A macro is not an operator and
has no templates, so it gets a smaller record: name, parameters, body text, source line.
The parser reads it from the same file in the same pass. Macros are documented on one
page and not mixed with the operator reference.

**Why not extend the compiler.** A `-operatorjson=<file>` option in
`ng_RangerDocGenerator.rgr` would put the extraction in the compiler and give the same
data to other consumers (the VS Code extension, a future language server). It is the
better long-term home for the A2 part. It is not the first step, because it needs a JSON
writer with correct escaping in Ranger, and each iteration needs a compiler rebuild. It
also cannot replace A1: the compiler emits the operators of one compilation, and the
reference must cover every library in the tree, including the libraries that a program
does not import. Stage A uses the public parser and the public API now; if the model
proves stable over two or three releases, the A2 part moves into the compiler.

### Stage B — example compilation

`docs/tools/build-examples.mjs`

Input: the example files in `docs/examples/**.rgr`. Output: for each example, the
generated code for each target language.

Measured cost on this machine, one Node process, `dist/api.js`, warm:

| Path | Time per (example, target) |
| --- | --- |
| CLI, `node bin/output.js` per compile | 180–250 ms, plus process start |
| In process, `VirtualCompiler.run()` | 148–250 ms |

The in-process path is used. With 12 target languages and, for example, 120 example
files, a full build is about 1200–1800 s single threaded. Three mechanisms keep the
release build inside a few minutes. **The implementation has the cache today and
compiles the examples one after the other; the worker pool is not necessary while the
example set is small (10 files, 120 compilations, approximately 15 s).**

1. **Worker pool.** `node:worker_threads`, one compiler instance per worker,
   `os.availableParallelism()` workers. Compilation is CPU bound and independent per
   example, so the speedup is close to linear.
2. **Content-addressed cache.** The key is
   `sha256(example source + target + Lang.rgr + stdops.rgr + compiler build id)`. The
   cache is stored in `docs/.cache/examples/` and restored in CI with
   `actions/cache`. A release that does not change the compiler recompiles nothing.
3. **Grouped examples.** One example file can demonstrate several operators of the same
   group (all bitwise operators, for example). The file declares which operators it
   covers, so 680 definitions do not need 680 files.

**Virtual filesystem.** The compiler runs with `use_real = false` and an in-memory
filesystem, in the same way as the playground
(`playground/scripts/build-compiler-env.mjs`). No temporary files, no output directory,
and the generated code is read from `res.fileSystem`. Note for the implementation: with
`use_real = true` the `-d` path is resolved against the working directory and the
compiler writes to disk; the virtual environment avoids both effects.

**Library examples.** The in-memory filesystem holds every file of `lib/`, so an example
that documents a library operator only needs its `Import` line. The playground environment
loads five library files; the documentation environment loads all of them, because the
reference covers all of them. An example for a library that a target cannot support (the
DOM operators outside JavaScript, for example) records the compiler diagnostic, and the
page then states the true target set of that library.

**Failures are data, not build breaks.** If an example does not compile for a target,
the result records the compiler diagnostic. The page then shows "no template for this
target" or the error text, which is accurate information about the compiler. A failure
for **every** target is a broken example and does break the build.

### Stage C — page rendering

`docs/tools/render-pages.mjs`

Writes MDX into `docs/site/src/content/docs/reference/` and JSON into
`docs/site/src/data/`. Both directories are in `.gitignore`: they are build output, and
a generated file in git produces review noise on every release.

One page per operator category, and one anchor per operator. This keeps the page count
near 25 instead of 680, keeps the sidebar readable, and lets the reader use in-page
search. Operators with much material (`forEach`, `switch`, the buffer operators) get a
dedicated page; the rule is a size threshold in the renderer, not a hand-kept list.

Per operator the page contains:

1. The signature, from the model.
2. The prose, from `docs/descriptions/<id>.md`, if the file exists.
3. The example source, as Ranger code.
4. A `<Tabs syncKey="target">` block with the generated code per target.
5. A target support row: which targets have a template, which use the `*` fallback,
   which have none.
6. A source link to `compiler/Lang.rgr` at the definition line.

### Stage D — coverage report

`docs/tools/check-coverage.mjs` writes `coverage.json` and prints a table:

| Metric | Gate |
| --- | --- |
| Operators with an example, per source | Warn under the recorded baseline, fail if it falls |
| Operators with prose, per source | Same, ratchet only upward |
| A file with an `operators { }` block that is not in `docs/sources.json` | Fail. A new library must be added to the reference in the same pull request |
| A parsed definition that no probe program registers | Report. The operator is unreachable |
| Targets declared in the `targets` block of `Lang.rgr` but with no template anywhere | Report |
| Targets that appear in templates but are not declared in the `targets` block | Report. `rust` is in this state now: 130 templates, not in the `targets` block |
| Targets in the CLI `-l` help text but not in the `targets` block | Report. The CLI lists 12 targets, the block lists 16 (`es5`, `ts`, `flow`, `nim`, `llvm` differ) |

The ratchet is a JSON baseline file in git. A release cannot lower coverage without an
explicit edit of the baseline, and the report page is published with the site, so the
gaps are visible instead of implied.

## 5. Example file format

An example is a normal, compilable Ranger program with a metadata header in comments.
It must compile, because the whole point is that the output is real.

```ranger
;; id: core/mod.int.int, core/div.int.int
;; title: Integer remainder and division
;; category: numeric
;; targets: es6, go, python, rust, kotlin, java7, cpp, csharp, php, scala, swift6
;; region: demo

class Main {
    sfn m@(main):void () {
        def a 7
        def b 3
        def rem (% a b)
        def quot (/ a b)
        print ("" + rem + " " + quot)
    }
}
```

| Key | Meaning |
| --- | --- |
| `id` | The operator identifiers that this example documents. The renderer places the example under each of them. |
| `title` | Heading for the example block. ASD-STE100 applies. |
| `category` | Cross-check against the model; a mismatch fails the build. |
| `targets` | Optional. Default is every target that has a template for the operator. A short list keeps a page small. |
| `region` | Optional. The name of the function whose body the page shows. Default is the main function. |
| `imports` | Optional. The libraries that the example needs, for example `JSON.rgr`. The `Import` lines in the source are the truth; this key only lets the build check that the example matches the source of the operator that it documents. |

Files live under `docs/examples/core/<category>/<id>.rgr` for the core operators and
`docs/examples/lib/<source id>/<id>.rgr` for the library operators. The examples are
ordinary files in the repository, so `npm run docs:examples` compiles them and any Ranger
test runner can also execute them.

### Output excerpt extraction

The generated file contains a preamble that is noise for an operator page. This is the
real ES6, Go and Python output for the example above:

```js
class Main  { constructor() { } }
function __js_main() {
  const a = 7; const b = 3;
  const rem = a % b; const quot = a / b;
  console.log("" + rem + " " + quot);
}
__js_main();
```

```go
package main
import ( "strings"; "strconv"; "fmt" )
type GoNullable struct { value interface{}; has_value bool }
type Main struct { }
func CreateNew_Main() *Main { me := new(Main); return me; }
func main() {
  var a int64= int64(7); var b int64= int64(3);
  var rem int64= a % b; …
}
```

The page shows the marked region by default and the full file behind a second tab. The
extractor works per target family:

| Family | Rule |
| --- | --- |
| Brace languages (`es6`, `ts`, `go`, `java7`, `kotlin`, `scala`, `csharp`, `cpp`, `php`, `rust`, `swift3`, `swift6`) | Find the line that declares the region function, then match braces to the closing brace. Remove the common indentation. |
| `python` | Find the `def <region>` line, then take the lines with a greater indentation. |
| `llvm` | Find the `define …@<region>` block, then read to the closing brace. |

If the rule finds nothing, the page shows the full file and the coverage report records
an extraction miss. A silent partial excerpt is worse than a complete file, so the
fallback is always the complete file. The extractor is a pure function over a string and
has unit tests per target family in `tests/`.

## 6. Page structure and a worked example

The generated Markdown for one operator, as the reader gets it:

---

### `%` — remainder

`int % (left: int, right: int) → int`

The `%` operator gives the remainder of an integer division. The sign of the result
follows the target language. For a negative left operand, the result is negative in C,
Go, Rust and JavaScript. It is not negative in Python.

**Ranger**

```ranger
def rem (% a b)
```

**Generated code** (tabs, synchronized across the site)

| Target | Output |
| --- | --- |
| JavaScript | `const rem = a % b;` |
| Go | `var rem int64= a % b;` |
| Rust | `let rem : i64 = a % b;` |
| Python | `rem = a % b` |

**Target support**: template for es6, go, rust, python, java7, kotlin, scala, csharp,
cpp, php, swift3, swift6. No template for llvm.

**Definition**: `compiler/Lang.rgr:1395`

---

The prose above is the part that a person writes, into
`docs/descriptions/numeric/mod.int.int.md`. Everything else comes from the model and
from the compiler. A missing description file leaves the section empty and adds a line
to the coverage report.

The reference alone does not tell a reader what the language is for. The site map:

```

  language/
    syntax                     s-expressions, blocks, comments
    types                      int, double, string, char, boolean, fixed-width types
    optionals                  <optional>T, wrap, unwrap, ??, null?, strict mode
    collections                arrays, hashes, immutable collections
    classes                    class, record, systemclass, constructors, traits
    functions                  fn, sfn, lambdas, chaining
    control-flow               if, switch, while, forEach, forUntil, try/throw
    memory                     weak, strong, lives, temp; what each target does with them
    processes                  the process model and its target mapping
    plugins                    compiler plugins, polyfills, pragma annotations
```

## 8. ASD-STE100 Simplified Technical English

The site text follows ASD-STE100 Issue 9 (published 15 January 2025): 53 writing rules
and a dictionary of about 900 approved words, each with one meaning and one part of
speech. The specification is available from
[asd-ste100.org](https://asd-ste100.org/).

### Rules that this site applies

| # | Rule | Application here |
| --- | --- | --- |
| 1 | Use approved words only, or a Technical Name, or a Technical Verb | The project dictionary in Section 8.2 lists the permitted technical terms |
| 2 | One word, one meaning; one part of speech | "compile" is a verb. Use "compilation" or "the compiler" for the noun. Never "a compile" |
| 3 | Short sentences: 20 words maximum in a procedure, 25 in a description | Enforced by the linter |
| 4 | One instruction per sentence | Steps are numbered lists |
| 5 | Active voice in procedures | "The compiler writes the file", not "The file is written" |
| 6 | Simple tenses only: present, past, future | No "will have been" |
| 7 | Do not remove articles | "Set the flag", not "Set flag" |
| 8 | Do not use a gerund or a participle as a noun | "The compilation of the file", not "Compiling the file" |
| 9 | Same word for the same thing every time | "target language", never "backend", "platform" or "output language" |
| 10 | Paragraph: one topic, 6 sentences maximum in a procedure | |
| 11 | Warnings and cautions before the step | Applies to destructive CLI flags |
| 12 | No slang, no jargon, no humour, no promotional language | Section 8.3 |

### 8.2 Project dictionary

Technical Names (nouns) that the site uses, and that the linter accepts:

```
Ranger, compiler, operator, template, target, target language, type, optional,
class, record, function, lambda, block, statement, expression, argument, parameter,
array, hash, buffer, string, integer, node, playground, repository, release, flag,
annotation, plugin, polyfill, process, module, package, source file, output file
```

Technical Verbs (manufacturing processes):

```
compile, parse, generate, write, read, install, run, build, publish, deploy, cache
```

Each new term is added to this list with the pull request that introduces it. The list
is a file, `docs/style/technical-names.txt`, not a section of prose.

### 8.3 Words that the site does not use

The request asks for technical text and not for advertisement. The linter rejects:

```
powerful, blazing, blazingly, seamless, seamlessly, effortless, effortlessly,
simply, just, easy, easily, elegant, beautiful, amazing, awesome, incredible,
revolutionary, cutting-edge, state-of-the-art, first-class, world-class, robust,
lightning-fast, super, magic, magical, delightful, love, loved, perfect
```

Two more categories are rejected for accuracy and not for tone: contractions
("doesn't", "it's") and vague quantities ("some", "several", "a lot of") where a number
is available.

### 8.4 Linting

[Vale](https://vale.sh/) runs over `docs/**/*.md` and `docs/**/*.mdx`, with a project
style in `docs/style/vale/RangerSTE/`:

| Rule file | Type | Checks |
| --- | --- | --- |
| `SentenceLength.yml` | `occurrence` | 25 words maximum, 20 in a page marked as a procedure |
| `Passive.yml` | `existence` | Forms of "to be" with a past participle |
| `Gerund.yml` | `existence` | A sentence that starts with an `-ing` word |
| `Marketing.yml` | `substitution` | The list in Section 8.3, with a suggested replacement |
| `Contractions.yml` | `substitution` | `doesn't` → `does not`, and the rest |
| `Terms.yml` | `substitution` | `backend`/`platform` → `target language`, and the rest |
| `Headings.yml` | `capitalization` | Sentence case |

**Limit, stated honestly:** the complete approved-word check needs the ASD-STE100
dictionary, and that dictionary cannot be redistributed inside this repository. The
linter therefore checks the mechanical rules (sentence length, voice, gerunds,
consistency, the reject lists) and not the full word list. The pull request checklist in
`contributing/writing-rules` carries the rules that the linter cannot check, and the
dictionary is available free of charge from asd-ste100.org for a manual check.

The linter runs on the handwritten pages and on `docs/descriptions/**`. It does not run
on generated code, on operator names or on compiler diagnostics.

## 9. Publication on a release

### Trigger

`deploy-pages.yml` gets one more trigger and one more path filter:

```yaml
on:
  push:
    branches: [main, master]
    paths:
      - "playground/**"
      - "gallery/game_engine/web/**"
      - "compiler/**"
      - "lib/**"
      - "docs/**"                       # new
      - ".github/workflows/deploy-pages.yml"
  release:
    types: [published]                  # new: the site follows every npm release
  workflow_dispatch:
```

and one more build block, before the "Assemble site root" step:

```yaml
      - name: Install docs dependencies
        working-directory: docs/site
        run: npm ci

      - name: Restore example compilation cache
        uses: actions/cache@v4
        with:
          path: docs/.cache
          key: docs-examples-${{ hashFiles('compiler/Lang.rgr', 'lib/stdops.rgr', 'docs/examples/**') }}
          restore-keys: docs-examples-

      - name: Generate the operator reference
        run: npm run docs:generate         # stages A, B, C, D

      - name: Lint the documentation text
        uses: errata-ai/vale-action@reviewdog
        with:
          files: docs

      - name: Build the docs site
        working-directory: docs/site
        run: npm run build

      - name: Copy the docs site into the artifact
        run: cp -r docs/site/dist/. "$GITHUB_WORKSPACE/_site/docs/"
```

The compiler is already built earlier in the job (`npm run compile`), so the reference
is generated with the compiler of that commit. This is the property that the request
asks for: the documentation and the compiler cannot drift apart, because the examples
are compiled by the same binary that the release publishes.

The release trigger checks out the tag, so a release publishes the documentation of that
tag. A push to master publishes the documentation of master. The header of the site
states which one the reader sees; see below.

### Version identity

Every page footer and the site header carry the version from `package.json` and the git
description:

```
Ranger 3.2.0 · built from a1b2c3d · 2026-08-01
```

For a build that is not a release tag the header adds "development build". A reader who
finds an operator that does not exist in the released npm package can then see why.

### The versioning question

Starlight has no built-in versioned documentation. Three options were considered:

| Option | Cost | Decision |
| --- | --- | --- |
| A. One version only, plus a version label and a generated change page | Low | **Chosen** |
| B. `starlight-versions` plugin | Medium; the plugin is in early development, and each release commits a content snapshot | Later, if a user asks for old versions |
| C. Copy each release build into `/Ranger/docs/v<version>/` | The Pages artifact is rebuilt from scratch each time, so old builds must be kept in git or fetched from the previous deployment. Both are fragile | Rejected |

Option A gives most of the value of versioning for a compiler project, because the
reader's real question is not "what did 3.1 do" but "what changed". That question is
answered by data that the pipeline already has:

**`reference/changes`** is generated by a diff of `operators.json` between the previous
release tag and the current one:

- operators added
- operators removed
- signature changes
- targets added or removed per operator
- generated output that changed for an unchanged operator (a template edit)

The last item is the most useful and the hardest to get by hand: it shows when a
compiler release changes the emitted code for a program that did not change. The diff is
computed from the two JSON models plus the two example outputs, and the previous model
is fetched from the previous git tag in CI.

## 12. Risks

| Risk | Effect | Response |
| --- | --- | --- |
| Compiler API change breaks Stage A | The release build fails | The model test runs against a fixture in CI, so the break appears in the pull request that causes it, not on release day |
| A new library adds operators and nobody adds it to `docs/sources.json` | The reference is incomplete and looks complete | `docs-sources.test.ts` searches the tree for `operators { }` blocks and fails on an unregistered file |
| The parser output and the compiled descriptors disagree | Wrong or duplicated entries | A3 reports both directions of the difference, and Stage D counts them. The join key is the source line, which both readers give |
| A full example build is slow | Release delay | Cache by content hash, worker pool. A release that does not touch the compiler recompiles nothing |
| 680 definitions, few examples | Thin reference at M3 | The reference degrades to the current `operators.md` level per operator, which is not a regression. The coverage page states the number |
| Only 12 operators have `@doc` | Little prose | Prose goes into `docs/descriptions/`, not into `Lang.rgr`, so a writer needs no compiler change and the text is linted |
| `starlight-versions` is early software | A future versioning move is not free | The generator writes plain MDX, so the plugin can be added later with no change to stages A–D |
| Pages holds one deployment | A separate docs workflow would delete the playground | The docs build is a step of `deploy-pages.yml`, and the workflow already documents this constraint |
| ASD-STE100 dictionary cannot be redistributed | The linter is a subset | The mechanical rules are automatic; the word list is a review step, and the specification is free to download |
