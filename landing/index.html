Rewrite?
Use Ranger.

There is no Silver Bullet.

Ranger is more like golden1. But it's not Magic. It emits ordinary source in the language you already ship: Swift for Apple platforms, Kotlin for Android, JavaScript for the browser.

1) An automated software testing method that compares the actual output of a program against a trusted baseline—known as a “golden file” or “golden master”.

Stay Dry.

Are you maintaining a separate harness to keep logic in multiple platforms in sync? Well, Ranger is the harness. Most programs do not need very complex code, but they need a way to verify the execution against a common logic. If you ever get that situation, then Ranger might just be the thing.

The problem

Native apps
without duplicating the logic

If you build iOS and Android separately, the UI can stay native — SwiftUI on iOS, Compose on Android — but shared business logic often gets implemented twice.

That means two copies of things like:

  • validation
  • pricing and calculations
  • state machines
  • parsers
  • sync rules
  • domain models

The implementations may start out identical, but they can drift as the applications evolve.

What Ranger changes

With Ranger, the shared logic has one source file and is compiled to both Swift and Kotlin. 

shared Ranger source
         |
    +----+----+
    |         |
  Swift     Kotlin
    |         |
 SwiftUI   Compose

The platform UI stays native. Only the logic that should behave the same on both platforms is shared.

No bridge or shared runtime

Ranger generates ordinary Swift and Kotlin source code.

The iOS application calls the generated Swift classes normally. The Android application calls the generated Kotlin classes normally.

There is no JavaScript runtime, cross-language bridge, message protocol or serialization layer between the UI and the shared logic.

Swift

let result = pricing.calculate(order)

Kotlin

val result = pricing.calculate(order)

Both calls can originate from the same Ranger implementation.

One implementation to maintain

If a rule changes, you change it once:

Pricing.rgr
    | compile
Pricing.swift
Pricing.kt

The generated files can be checked into the repository, reviewed in diffs and tested with the normal platform toolchains.

This keeps the part that must stay identical in one place, while leaving the parts that should be platform-specific native.

Native UI. Shared logic. One source of truth.

01 — Kotlin

Kotlin — 69%

What works well

  • A loop whose body ignores its index is for (v in xs).
  • Optionals become normal Kotlin nullable types such as T?.
  • Ranger shape types become sealed interfaces with implementing classes.
  • Function parameters use Kotlin function types such as (Int) -> Int.
  • Exceptions compile to normal Kotlin exceptions.
  • Shared objects use normal JVM reference semantics.

Current limitations

  • Ranger Enum is still represented as an Int.
  • Generic classes are monomorphized, for example Stack_int.
  • Ranger traits are usually mixins rather than Kotlin interfaces.
  • There is no native Result model.
  • Some interface cases are still incomplete and can produce uncompilable output.

02 — Python

Python — 67%

What works well

  • A loop whose body never reads the index is for v in xs:, not enumerate.
  • Classes and shared-object semantics map naturally to Python.
  • Optionals use None.
  • Null fallback produces normal Python conditional expressions.
  • Loops can use enumerate.
  • Exceptions use normal try, except and raise.
  • main uses the standard if __name__ == "__main__" pattern.
  • Larger lambdas can be emitted as regular functions.

Current limitations

  • Generated code has no Python type hints.
  • Records do not become dataclass types.
  • Ranger enums do not become enum.Enum.
  • Shapes use generated classes and _rg_kind tags instead of match.
  • Traits copy methods instead of becoming protocols.
  • Generics are monomorphized.

03 — Dart

Dart — 66%

What works well

  • A loop whose body ignores its index is for (final v in xs).
  • Optionals become T?.
  • Lists and function types use normal Dart syntax.
  • Generated programs have a regular top-level main.
  • Exceptions use Dart throw and catch.
  • Shared objects use normal Dart reference semantics.

Current limitations

  • Ranger records become mutable classes rather than Dart records.
  • Shapes do not yet use modern Dart sealed classes and switches.
  • Ranger enums are integers.
  • Null fallback is emitted as a ternary rather than ??.
  • Generics are monomorphized.
  • Weak references are not preserved.

04 — C#

C# — 65%

What works well

  • A loop whose body ignores its index is foreach (T v in xs).
  • Nullable primitive types use forms such as int?.
  • Collections use List<T>.
  • Function values use Func<...>.
  • Shared objects use normal C# reference semantics.
  • Exceptions compile and preserve the message.

Current limitations

  • Domain errors currently use ConfigurationErrorsException.
  • Ranger enums are integers.
  • Generic Ranger classes become specialized classes such as Stack_int.
  • Traits are not emitted as modern C# default-interface implementations.
  • There is no native record or Result mapping.

05 — PHP

PHP — 59%

What works well

  • Objects use normal PHP reference semantics.
  • Optionals use null.
  • Exceptions compile to normal PHP Exception handling.
  • Entry code is emitted at file scope.

Current limitations

  • Generated fields use older var $x style.
  • Type information is mostly absent.
  • Ranger enums become integers.
  • Ranger traits are not emitted as PHP traits or interfaces.
  • Generics are monomorphized.
  • The result is closer to working PHP script code than modern typed PHP.

06 — Scala

Scala — 57%

What works well

  • Optionals use Scala Option[T], Some and Option.empty.
  • Shape dispatch uses Scala match and case.
  • Entry code uses an application object.

Current limitations

  • Control-flow returns still use a generated exception helper.
  • Shape cases are ordinary classes rather than Scala enums or case classes.
  • Ranger enums are integers.
  • Ranger traits are not emitted as Scala traits.
  • The generated source still looks strongly like translated code.

07 — Swift

Swift — 57%

What works well

  • A loop whose body never reads the index is for v in xs, not enumerated().
  • Optionals become normal Swift T?.
  • Null fallback uses ??.
  • Weak references become weak var.
  • Ranger shapes become Swift enums with associated values.
  • Exceptions use throws and try.
  • Object sharing follows Swift's ARC model.

Current limitations

  • Ranger enums are still integers.
  • Traits are only partly representable as Swift protocols.
  • Field-bearing traits cannot be represented directly.
  • There is no Result mapping.
  • Generics are monomorphized.

08 — TypeScript

TypeScript — 56%

What works well

  • A loop whose body ignores its index is for (const v of xs).
  • Generated JavaScript receives useful TypeScript annotations.
  • Optional strings become string | undefined.
  • Shapes get union aliases.
  • Shape cases carry typed discriminators.
  • Method signatures are valid TypeScript.

Current limitations

  • Null fallback still uses generated ternary checks rather than ??.
  • Generic classes become specialized types such as Stack_int.
  • There is no Result<T, E>.
  • Shape handling does not yet produce idiomatic discriminated-union switches.
  • Ranger enums remain numbers.

09 — JavaScript

JavaScript — 56%

What works well

  • A loop whose body ignores its index is for (const v of xs).
  • Ranger's object, array and function semantics map naturally to JavaScript.
  • Shared values use normal object identity.
  • Exceptions work using native JavaScript throw and catch.
  • This is also the compiler's primary self-hosting target.

Current limitations

  • Optionals still use explicit typeof checks.
  • Modern syntax such as ?? and optional chaining is not used.
  • Shapes use generated classes and tags.
  • Ranger enums become numbers.
  • Weak references are not preserved.
  • Generated entry code is not structured as an ES module.

10 — Java

Java — 51%

What works well

  • A loop whose body ignores its index is the enhanced for (T v : xs).
  • Generated programs compile and run.
  • Exceptions use normal Java exceptions.
  • Objects use normal Java sharing semantics.
  • Files already follow Java's one-public-class-per-file structure.

Current limitations

  • The backend targets an older Java style.
  • Optionals use boxed values and null.
  • Ranger enums become integers.
  • Function values use generated helper classes rather than lambdas.
  • Generics are monomorphized.
  • Modern Java records, sealed types and related features are not used.

11 — Rust

Rust — 46%

What works well

  • Ranger records can become Rust structs.
  • Read-only methods and parameters can use &self, &T, &str and slices.
  • Shared mutable classes use Rc<RefCell<T>> when the ownership analysis requires it.
  • Weak optional back-references use Option<Weak<RefCell<T>>>.
  • Optionals use Option<T>.
  • Shapes can become native Rust enums.
  • Pattern matching can use native match.
  • Generated names use snake_case.
  • A behaviour-only trait used as a type is a real trait with one impl per consumer.
  • A file with no shared class carries no Rc, RefCell or downcast helper.

Current limitations

  • Ranger has no native Result<T, E> or ?.
  • There are no user-visible lifetimes.
  • Rust standard traits cannot yet be implemented directly.
  • Iterator adapters are not generated.
  • Generic Ranger classes are monomorphized.
  • try / throw is currently rejected instead of being lowered to Rust error handling.

12 — C++

C++ — 45%

What works well

  • Weak references can use weak_ptr.
  • Shared ownership can use shared_ptr.
  • Ranger enums can become enum class in supported cases.
  • Shapes can use std::variant.
  • Function values use std::function and lambdas.
  • Exception messages are preserved in supported cases.

Current limitations

  • Too many values are represented through shared_ptr.
  • Records that should be value types can still become heap objects.
  • Read-only parameters often receive shared pointers rather than references.
  • Optionals do not use std::optional.
  • There is no std::expected mapping.
  • Some optional primitive cases do not compile.
  • Some interface cases still reference missing generated types.
  • Integer width can differ from other Ranger targets.

13 — Go

Go — 39%

What works well

  • Shared objects map to pointers.
  • Function parameters can become normal Go function types.
  • Methods use pointer receivers.
  • Generated programs can compile and produce the expected results.
  • A loop whose body ignores its index is for _, v := range xs.

Current limitations

  • Optionals use a Ranger-specific nullable wrapper.
  • The ownership analysis the C++ and Rust writers read does not run for this target at all.
  • Weak/optional object references do not map directly to normal Go pointers.
  • Shapes use tagged structs rather than native Go-style interfaces or errors.
  • Ranger enums become integers.
  • Traits do not naturally become Go interfaces.
  • try / throw relies on panic / recover.

Summary

What is consistent across targets

The strongest generated source currently comes from Kotlin, Python, Dart and C#. Their basic object, optional and control-flow models map reasonably well to Ranger.

Recently closed, on every target at once

  • A loop whose body ignores its index is now that language's own loop over the collection — for...of, range, the enhanced for, foreach, for v in xs — rather than a C-style index loop. One analysis, thirteen spellings.

Largest remaining problems

  • Ranger enums often become plain integers instead of native enums.
  • Generic classes are usually monomorphized. This is the lowest score on every one of the thirteen targets.
  • Ranger traits do not consistently map to native interface or trait systems.
  • There is no portable Result abstraction.
  • Some targets still need better native optional handling.
  • C++ and Rust read an ownership analysis Go does not run at all.

Platforms

From a watch to a Raspberry Pi
to a browser tab.

Getting a program to run somewhere takes more than a target language: a build, a host, and a way to talk to the screen and the filesystem. That plumbing is in the repository, written in Ranger, for each of these.

01 — Apple

iOS, iPadOS, watchOS

Swift out, and the build itself is a Ranger program. lib/apple/ invokes xcrun, swiftc, plutil, codesign and simctl directly, straight to an installed, running app — without generating an .xcodeproj or invoking xcodebuild. 151 checks assert the plan it produces, which program with which arguments in which order, and they run on JavaScript, Python, Go, Rust, C++, Java and PHP, on any machine, with no Mac in sight. On a Mac, one command puts the app on the simulator; another puts it on the phone on the cable, finding the device, the signing identity and the provisioning profile rather than asking you to type them.

02 — Android

Kotlin and android.graphics

Kotlin with @JvmField, MutableList and the collection types the JVM expects, using the platform's own types directly. The PowerPoint stack is the demonstration: the same Ranger source drawn with android.graphics on the device and with Java2D on any JVM, so the port can be checked on a build server without a phone. The port itself is a facade, one walk over the display list, and two implementations of an eight-method surface.

03 — Web

Node.js and the browser

ES2015 or TypeScript, ESM or CommonJS, with source maps and a package.json when you ask for one. Node is the compiler's own official host — the playground on this site is the compiler, compiled to JavaScript and running in your tab, which is also the shortest description of what self-hosting buys you.

04 — Desktop

SDL2, GLES2 and native binaries

The game engine's C++ path opens an SDL2 window with a GLES2 present path, gamepad input through SDL GameController, and the engine's own audio synth. The same catalogue of games runs unchanged in a browser tab over a virtual filesystem. Headless builds take a frame count and SDL_VIDEODRIVER=dummy, so the window is optional and the same build runs headlessly in CI.

05 — Single board

Raspberry Pi

A deploy script rsyncs the repository to a Pi 5, compiles the SDL2 + GLES2 host on the device — wasm3 included, so WASM games load from committed modules with no Rust toolchain on the board — and wires an autostart. Or you take the offline aarch64 bundle, which is a terminal build that needs no SDL at all. Develop on the desktop and run the same logic on the hardware — which is what the engine was built for.

06 — Servers and tools

Go, Rust, C++, LLVM

Go and Rust for services, C++ for the fast path, LLVM for a lower-level native compilation path that skips the C++ source step. One compiler primitive runs other programs — run_process_result, which answers exit code, stdout and stderr, takes a working directory and extra environment entries, and passes its arguments as a vector so nothing inside one is ever re-read by a shell. It has a back end on thirteen targets, and the library over it records a dry run instead of executing, which is what makes a build driver testable.

EVG

A layout and rendering engine,
written in the language.

EVG lays out a tree with a substantial CSS feature set — flex, grid, the cascade, @media, TrueType metrics and GPOS kerning — then walks it once and emits flat draw commands: filled rect, border, image quad, text run, push and pop clip. Absolute pixels, colours resolved, no tree and no units left. Everything below that seam knows only about quads, glyph runs and scissor rectangles, which is why the same page comes out of six painters.

CSS layout and cascade

Flex and grid, specificity and the cascade, border radius, shadows, transforms, overflow: hidden as a real clip, and @media blocks that fold a side rail into a bottom bar at 768px — in a PDF as much as on a GPU.

Effects on the GPU

Blur, rotation, sub-pixel shift and the surface ripple behind the top of this page. Each has an oracle — a reference implementation the GPU path is checked against on every push — so an effect cannot quietly stop matching the layout.

And a vectoriser

A bitmap tracer: edge walk, corner detection, curve fitting, colour posterising. It reads a PNG or a JPEG and writes paths — and it is what turned Ranger's own logo into the vector on this page. See the showcase →

Getting started

From zero to Ranger

The language itself is small: compiler/Lang.rgr declares 336 core operator definitions under 207 names, and the generated reference documents 838 operators once the standard library is counted in. The way in is not to read all of that first, and it is not to clone this repository either — this is the compiler, the gallery and their own test corpus, which is what you clone to work on Ranger. To write a program in it, the compiler is an npm package and RangerStarter is a project already built around it.

01

Start from the starter

Node is the compiler's official host and the only thing the compiler itself needs. Nothing is installed globally: ranger-compiler is a dependency of your project, so the compiler your program is compiled with is the one your package.json names. The starter is two source files, a test that fails properly, and a build loop — MIT, so keep what you want and delete the rest. 

git clone https://github.com/terotests/RangerStarter my-app
cd my-app && npm install
npm start

02

Compile it where you are going

One flag decides the target, and the output is ordinary source you read in the diff. Generating Swift does not need Xcode, so the whole matrix compiles on the machine you already have; running it is the target toolchain's business. targets:run executes the three a plain machine has and fails when their output differs — which is the only thing that actually checks a portability claim. 

npm run targets       # all fourteen writers
npm run targets:run   # runs three, and compares
npx rgrc -l=kotlin src/Main.rgr

03

Change one thing

Open src/Main.rgr, change the program, and run it again. The .rgr file stays the source of truth; generated target files are disposable and can always be recreated. 

$EDITOR src/Main.rgr
npm start
npm run targets:run

The output is still ordinary source code, not an opaque artifact. Open it when you are curious, diff two targets when something behaves differently, and run it with the target's normal tools. Edit Ranger; inspect everything.

04

Then the gallery, when you need it

gallery/ here is the corpus: parsers for TypeScript, C++ and JavaScript, a spreadsheet, a PowerPoint stack, a game engine, a chart runtime, a node-graph editor, a Figma reader, and EVG — a CSS layout engine with no browser in it. The starter pulls any of them in as a pinned dependency, and says what that costs before it does: the gallery is AGPL-3.0-or-later while the compiler, the runtime and your own program stay MIT. Clone this repository when you want to read the whole corpus or change the compiler. 

scripts/add-gallery.sh        # the list, and the cost
scripts/add-gallery.sh evg

Reading first: the documentation has install, types, optionals, traits, generics and the operator reference generated from the sources of the commit that published it, and the FAQ it links is the shortest path past the errors that otherwise cost an extra edit–compile cycle. Trying before installing anything: the playground compiles Ranger in your browser with nothing installed. Working with an agent anywhere else: /plugin marketplace add terotests/Ranger installs the same skills the starter carries.

Where it stands today

Ranger is experimental. Target quality varies by language and by feature area, several gallery projects need toolchains you may not have, and you should expect to fix a bug or add a capability now and then. It is stronger as a portable-algorithm compiler and DSL toolchain than as a drop-in replacement for a mainstream application language — and it is used that way, daily, on programs as large as itself.
