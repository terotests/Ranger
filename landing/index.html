What?

Ranger is a small, typed language — classes, traits, generics, lambdas, custom operators — with a source-to-source compiler. It emits ordinary source in the language you already ship: Swift for Apple platforms, Kotlin for Android, JavaScript for the browser, and eleven more back ends — fourteen in all — from the same file. The generated program depends on its own platform toolchain, and on no runtime of Ranger's.

Consistency is the point

One source for the logic that must not diverge, compiled into ordinary target-language code on every platform. Each side calls the shared classes and methods directly, in its own language, and what you review is ordinary platform source.

What actually changed

A common cross-platform trade-off is to write the app once and accept a bridge, an extra runtime and a layer between you and the platform. Coding agents have lowered the cost of producing platform-specific code, so that trade pays off less often than it did — and the second implementation gets written. Two independently maintained implementations can still drift apart over time.

What Ranger offers

Ranger handles the part code generation does not solve: keeping shared logic identical across targets. Compile the logic that must not diverge — the domain model, the pricing, the parser, the sync rules, the state machine — into checked-in Swift and Kotlin source, and write SwiftUI and Compose by hand, the way each platform wants them written.

Ordinary calls

The shared code arrives as Swift and Kotlin source, so each app calls it the way it calls its own: no cross-language bridge, no serialisation boundary and no additional Ranger runtime. The output is the language you already ship.

One source of truth

A shared rule can only be changed in one place, because the Swift and the Kotlin are generated from one file. Shared rules stay in step by construction rather than by convention — the user interfaces on each side stay hand-written.

Readable diffs

@JvmField and MutableList on Kotlin, final class on Swift, Rc<RefCell<T>> on Rust only where the sharing analysis says a class is shared. The generated code is checked in and reviewed like any other platform source.

Worked through at full size in this repository: gallery/pptx reads PowerPoint files, and the Android app is that same source compiled to Kotlin and drawn with android.graphics. The ZIP reader, the OOXML parser, the theme resolver, the JPEG and PNG decoders, the TrueType reader and the layout engine are all Ranger, and not one of them was forked for the port.

Targets

Fourteen back ends,
and a table of how far each one goes.

Target quality varies by language and by feature area. These are the tiers from TARGET_NOTES.md. CI compares the capability matrix against a checked-in baseline, so any change — a regression or an improvement — fails the build until the record is updated.

How the count works. -l= takes fourteen values, and that is the number of code-generating back ends. Two of them have a flag that changes the output language: -typescript on the JavaScript back end writes TypeScript, and -wat on the LLVM back end writes WebAssembly text. That is the sixteen rows below, and the fifteen columns of the syntax-app matrix, which covers every back end plus TypeScript.

Write for the strictest target

Garbage-collected targets — JavaScript, Go, Python, Kotlin, Dart, Java, C# — generally need fewer ownership annotations than C++, Rust and Swift's reference counting do. Wherever the object graph has a cycle or a non-owning edge, the ownership annotations (@(weak), @(strong), @(lives), @(temp)) have to say so. Code that runs happily on ES6 can still leak on C++ until they are added, and the compiler will print the ownership it inferred for every parameter when you ask it to.

Extending it is not a rebuild

compiler/Lang.rgr — the core operator table, 336 definitions under 207 names — is read at compile time, not baked into the binary. Add or change an operator template there and the very next compile uses it. The compiler looks in the working directory first, so a copy beside your sources overrides the installed one, which makes an experiment cheap to try and cheap to throw away. That is also how support for an older language version gets added: a custom operator behind a flag.

Platforms

From a watch to a Raspberry Pi
to a browser tab.

Getting a program to run somewhere takes more than a target language: a build, a host, and a way to talk to the screen and the filesystem. That plumbing is in the repository, written in Ranger, for each of these.

01 — Apple

iOS, iPadOS, watchOS

Swift out, and the build itself is a Ranger program. lib/apple/ invokes xcrun, swiftc, plutil, codesign and simctl directly, straight to an installed, running app — without generating an .xcodeproj or invoking xcodebuild. 151 checks assert the plan it produces, which program with which arguments in which order, and they run on JavaScript, Python, Go, Rust, C++, Java and PHP, on any machine, with no Mac in sight. On a Mac, one command puts the app on the simulator; another puts it on the phone on the cable, finding the device, the signing identity and the provisioning profile rather than asking you to type them.

02 — Android

Kotlin and android.graphics

Kotlin with @JvmField, MutableList and the collection types the JVM expects, using the platform's own types directly. The PowerPoint stack is the demonstration: the same Ranger source drawn with android.graphics on the device and with Java2D on any JVM, so the port can be checked on a build server without a phone. The port itself is a facade, one walk over the display list, and two implementations of an eight-method surface.

03 — Web

Node.js and the browser

ES2015 or TypeScript, ESM or CommonJS, with source maps and a package.json when you ask for one. Node is the compiler's own official host — the playground on this site is the compiler, compiled to JavaScript and running in your tab, which is also the shortest description of what self-hosting buys you.

04 — Desktop

SDL2, GLES2 and native binaries

The game engine's C++ path opens an SDL2 window with a GLES2 present path, gamepad input through SDL GameController, and the engine's own audio synth. The same catalogue of games runs unchanged in a browser tab over a virtual filesystem. Headless builds take a frame count and SDL_VIDEODRIVER=dummy, so the window is optional and the same build runs headlessly in CI.

05 — Single board

Raspberry Pi

A deploy script rsyncs the repository to a Pi 5, compiles the SDL2 + GLES2 host on the device — wasm3 included, so WASM games load from committed modules with no Rust toolchain on the board — and wires an autostart. Or you take the offline aarch64 bundle, which is a terminal build that needs no SDL at all. Develop on the desktop and run the same logic on the hardware — which is what the engine was built for.

06 — Servers and tools

Go, Rust, C++, LLVM

Go and Rust for services, C++ for the fast path, LLVM for a lower-level native compilation path that skips the C++ source step. One compiler primitive runs other programs — run_process_result, which answers exit code, stdout and stderr, takes a working directory and extra environment entries, and passes its arguments as a vector so nothing inside one is ever re-read by a shell. It has a back end on thirteen targets, and the library over it records a dry run instead of executing, which is what makes a build driver testable.

Proof

What the four gates
on every push measure.

Equivalent output across a dozen languages is easy to assert and hard to keep. These four run on every push and break the build when they stop agreeing, which is what keeps the claims on this page tied to the current compiler.

01

The syntax app, on fifteen outputs

One program that uses 203 of the 207 core operator names together with classes, inheritance, traits, records, enums, extensions, lambdas, optionals, buffers and custom operators. It is compiled to all fourteen back ends the CLI accepts, plus TypeScript, then built and run with node, tsc, go, python3, rustc, g++, javac, php and lli — whichever the machine has — and what each one printed is compared with the reference target. The result is a matrix asserted against a checked-in baseline, so an improvement requires an explicit update to the baseline just as a regression does.

02

Self-hosted across seven source targets, with LLVM verified separately

The compiler running on Node is the reference build. It also compiles itself to C++, Dart, Python, C#, Go and Kotlin — seven builds counting the reference. Each of those six is then handed the compiler's own source and asked for JavaScript, and the JavaScript that comes out is compared byte for byte with what the Node build writes for the same input: identical on all six, save for a single line on C++ (32-bit int). On LLVM, the 22 MB of IR the compiler emits for itself passes opt -passes=verify and links into a native rangerc, which reproduces the Node build's JavaScript byte for byte as well.

03

A JavaScript engine as the load test

gallery/game_engine/v2/interp is a JavaScript interpreter written in Ranger, which makes it the largest thing the cross-target gate has to carry: Go, Kotlin, Python, C#, Dart and Swift 6 each compile it, and where the toolchain is installed they build it and answer the benchmark cases. 1303 conformance cases are checked against Node's answers — a fast wrong answer fails the run. The C++ and Rust builds score 1297 of them with zero crashes, and the six failures are named and tracked rather than new. Performance is reported separately: on the C++ build, the geometric mean over the benchmark cases is about 4.4× QuickJS 2021-03-27 once the strcat case is excluded, and QUICKJS_COMPARISON.md gives the methodology and says why that row does not belong in the average.

04

Semantics, pinned as fixtures

The places targets disagree by nature are the places a portable program breaks: integer division promoting to double, array parameters passed by reference, Unicode string indexing by code point, line endings. Each one is a conformance fixture run on ES6, Go, Kotlin and Dart. Where a target has a known gap, the gap is named in the fixture rather than papered over.

Two more, for the rendering stack: EVG's SVG painter and its WebGL painter share no code and are differenced pixel for pixel over the same frames — 0.022% on a sheet built to exercise every draw command, 0.000% on every slide of a real .pptx deck. And the bitmap tracer that turned Ranger's logo into the vector on this page is compiled to Node, Python, C++ and Rust, with a smoke test asserting all four write the byte-identical SVG for the same input.

EVG

A layout and rendering engine,
written in the language.

EVG lays out a tree with a substantial CSS feature set — flex, grid, the cascade, @media, TrueType metrics and GPOS kerning — then walks it once and emits flat draw commands: filled rect, border, image quad, text run, push and pop clip. Absolute pixels, colours resolved, no tree and no units left. Everything below that seam knows only about quads, glyph runs and scissor rectangles, which is why the same page comes out of six painters.

CSS layout and cascade

Flex and grid, specificity and the cascade, border radius, shadows, transforms, overflow: hidden as a real clip, and @media blocks that fold a side rail into a bottom bar at 768px — in a PDF as much as on a GPU.

Effects on the GPU

Blur, rotation, sub-pixel shift and the surface ripple behind the top of this page. Each has an oracle — a reference implementation the GPU path is checked against on every push — so an effect cannot quietly stop matching the layout.

Colophon

The logo on this page
was vectorised by a tool written in Ranger.

Ranger's mark existed as a 304-pixel bitmap and nothing else. It went into lib/evg/tools/evg_trace_cli.rgr — the bitmap tracer — which posterised it into flat colour regions, walked the edges of each one, found the corners, fitted cubics between them and wrote back three layers, about 3 KB. That one file is the shield in the navigation bar, the tab icon, the drawing beside this paragraph and the mark in the backdrop at the top of the page, and it is sharp at every one of those sizes because none of them is the bitmap any more.

The backdrop at the top of the page is the same story one layer further on. It is an EVG display list, laid out at build time from a stylesheet and a tree, drawn on the GPU by the same WebGL painter the PowerPoint editor uses, and put through evg-surface-effect: ripple — a post-process that renders the finished surface into a texture and bends it in rings travelling out from each drop. Move the pointer across it; the rings interfere where they cross, because that is what summing waves does. 

node landing/tools/logo.mjs        # the mark
node landing/tools/hero.mjs       # the surface behind it
npm run evg:trace:cli:smoke       # four targets, one file, compared byte for byte

Getting started

From zero to a Ranger program,
in three commands.

The language itself is small: compiler/Lang.rgr declares 336 core operator definitions under 207 names, and the generated reference documents 838 operators once the standard library is counted in. The way in is not to read all of that first, and it is not to clone this repository either — this is the compiler, the gallery and their own test corpus, which is what you clone to work on Ranger. To write a program in it, the compiler is an npm package and RangerStarter is a project already built around it.

01

Start from the starter

Node is the compiler's official host and the only thing the compiler itself needs. Nothing is installed globally: ranger-compiler is a dependency of your project, so the compiler your program is compiled with is the one your package.json names. The starter is two source files, a test that fails properly, and a build loop — MIT, so keep what you want and delete the rest. 

git clone https://github.com/terotests/RangerStarter my-app
cd my-app && npm install
npm start

02

Compile it where you are going

One flag decides the target, and the output is ordinary source you read in the diff. Generating Swift does not need Xcode, so the whole matrix compiles on the machine you already have; running it is the target toolchain's business. targets:run executes the three a plain machine has and fails when their output differs — which is the only thing that actually checks a portability claim. 

npm run targets       # all fourteen writers
npm run targets:run   # runs three, and compares
npx rgrc -l=kotlin src/Main.rgr

03

Change one thing

Open src/Main.rgr, change the program, and run it again. The .rgr file stays the source of truth; generated target files are disposable and can always be recreated. 

$EDITOR src/Main.rgr
npm start
npm run targets:run

The output is still ordinary source code, not an opaque artifact. Open it when you are curious, diff two targets when something behaves differently, and run it with the target's normal tools. Edit Ranger; inspect everything.

04

Then the gallery, when you need it

gallery/ here is the corpus: parsers for TypeScript, C++ and JavaScript, a spreadsheet, a PowerPoint stack, a game engine, a chart runtime, a node-graph editor, a Figma reader, and EVG — a CSS layout engine with no browser in it. The starter pulls any of them in as a pinned dependency, and says what that costs before it does: the gallery is AGPL-3.0-or-later while the compiler, the runtime and your own program stay MIT. Clone this repository when you want to read the whole corpus or change the compiler. 

scripts/add-gallery.sh        # the list, and the cost
scripts/add-gallery.sh evg

Reading first: the documentation has install, types, optionals, traits, generics and the operator reference generated from the sources of the commit that published it, and the FAQ it links is the shortest path past the errors that otherwise cost an extra edit–compile cycle. Trying before installing anything: the playground compiles Ranger in your browser with nothing installed. Working with an agent anywhere else: /plugin marketplace add terotests/Ranger installs the same skills the starter carries.

Where it stands today

Ranger is experimental. Target quality varies by language and by feature area, several gallery projects need toolchains you may not have, and you should expect to fix a bug or add a capability now and then. It is stronger as a portable-algorithm compiler and DSL toolchain than as a drop-in replacement for a mainstream application language — and it is used that way, daily, on programs as large as itself.
